# 계정 찾기·비밀번호 재설정

상태: [PR #103](https://github.com/1213ghgo-kimdy1217/semiguard-ai/pull/103)의 검증 커밋 `f175079`를 승인받아 main `5be15513`에 병합하고 정식 사이트에 배포·활성화했습니다. 승인 커밋과 병합 결과의 트리 일치, 운영 health와 복구 availability, 합성 계정의 비밀번호 재설정·새 비밀번호 로그인을 확인했습니다. 사용자 직접 회원탈퇴 후 시험 계정·복구 이메일·토큰 삭제를 확인했고, 점검용 임시 연결정보 삭제와 도우미 종료도 완료했습니다.

2026-11-02 진행: 사용자가 승인한 Gmail로 Brevo 무료 계정과 전화 인증을 완료했고, 실제 화면에서 해당 발신 주소의 Verified 상태를 확인했습니다. 소유 도메인 인증은 하지 않았습니다. 분리 QA용 1개월·Transactional email 전용 키는 해당 브랜치의 Vercel Preview Secret에 저장했고, 별도 승인한 운영용 키는 Production 서버 Secret에 설정했습니다. 분리 QA에서는 인증·아이디 안내·아이디 기반 재설정·변경 알림·이메일 기반 재설정 메일 5건을 실제 INBOX에서 확인했습니다. 이후 별도 운영 검증에서도 같은 다섯 종류의 메일 5건이 실제 INBOX에 도달했습니다. 사용자가 재발송 없이 최신 원본 메일에서 비밀번호를 변경하고 새 비밀번호로 로그인했으며, 동일 합성 계정과 저장된 인증 이메일을 확인한 뒤 시험 계정을 정리했습니다.

분리 QA DB에서는 합성 계정 4개로 실제 TiDB 트랜잭션·동시 재설정·실패 시 원복·제한·세션 버전 등 18/18 항목을 확인하고 해당 계정을 정리했습니다. 누적 다섯 번째 합성 계정으로 실제 Preview 로그인과 메일 왕복을 확인한 뒤, 정확한 ID/openId의 계정·복구 이메일·토큰만 정리했습니다. 모든 공유 제한 카운터와 최대 6회 발송 시도 예산은 보존했고, 임시 연결정보를 지운 상태와 로컬 도우미 종료도 확인했습니다. 분리 QA DB로 실제 회원 자료를 복사하지 않았습니다. 이 기록은 별도로 완료한 운영 합성 계정 검증·정리와 구분합니다.

## 이용 흐름

- 로그인 화면의 회원가입 옆에서 **아이디 찾기 / 비밀번호 재설정**을 선택합니다.
- 아이디 찾기는 사전에 인증한 복구 이메일로 아이디를 보냅니다. 결과 화면에 회원정보나 계정 존재 여부를 표시하지 않습니다.
- 비밀번호 재설정은 **로그인 아이디 / 등록된 복구 이메일** 중 하나를 입력하고, 해당 계정의 인증된 복구 이메일로 받은 링크를 이용합니다.
- 기존 계정은 로그인할 수 있을 때 **계정 관리 → 복구 이메일 → 현재 비밀번호 재확인 → 이메일 링크 인증**을 먼저 해야 합니다. 기존 일반 회원가입은 이메일을 받지 않았으므로 이미 이메일 복구가 가능하다고 소급하여 주장하지 않습니다.
- 이메일을 인증하지 못한 계정은 이 기능으로 복구할 수 없습니다. 사전에 연결해 둔 소셜 로그인은 기존 방식대로 이용합니다. 이름·생년월일·공개 아이디만으로 비밀번호를 바꾸지 않습니다.
- 링크는 15분/1회용입니다. 새 비밀번호는 10~128자로 두 번 입력하고, 완료 후 새 비밀번호로 다시 로그인합니다. 기존 가입/로그인 요청 필드와 기존 비밀번호는 그대로 호환됩니다.

## 보존하는 계약

기존 회원 ID/openId, 비밀번호 해시, 소셜 제공자 ID 연결, 학습 기록·답안·점수·이어하기·공유·AI 동의 계약을 바꾸지 않습니다. 이메일이 같다는 이유로 소셜 계정을 연결하거나 기존 `users.email` 및 소셜 이메일을 인증 완료로 취급하지 않습니다.

세션 버전 `users.auth_version`의 초기값은 0입니다. 버전 없는 기존 세션은 버전 0 계정에 한해 유효합니다. 재설정은 토큰 확인/소비·해시 교체·버전 증가·기존 복구 토큰 제거를 한 트랜잭션에서 처리하고 이전 쿠키와 Bearer 세션을 차단합니다. 탈퇴 시 복구 이메일과 미사용 토큰도 같은 트랜잭션에서 제거합니다.

## 저장·전송 범위

| 항목 | 처리 |
| --- | --- |
| 복구 이메일 | 별도 테이블에 소유 확인 주소와 시각 저장. 계정당 하나, 확인 주소 키는 고유 제약. 기존 프로필 주소를 자동 수입하지 않음 |
| 일회용 토큰 | 32바이트 난수 원문은 메일로 전달, DB에는 SHA-256 해시·목적·계정·주소·언어·세션 버전·만료만 저장 |
| 남용 방지 | DB 기반 전역/클라이언트/입력값 제한과 최종 수신함 제한. 서버 키로 해시한 카운터만 저장하고 만료분을 제한된 수로 정리 |
| 브라우저 | URL fragment를 즉시 제거. local/sessionStorage에 토큰을 저장하지 않고 요청 뒤 비밀번호와 변경 요청 캐시 정리 |
| 메일 제공자 | Brevo 트랜잭션 REST 어댑터. 명시적 활성화 시 고정 HTTPS API로 발신·수신 주소와 안내 문구/아이디 또는 일회용 링크를 전송. 텍스트 본문만 사용하고 비밀번호·회원 답안은 보내지 않음 |
| 분석·로그 | 복구 경로는 기존 GA 페이지 허용 목록에 포함하지 않음. 복구 변경 요청의 전송 오류 객체·수신자·토큰·제공자 응답 본문을 출력하지 않음 |

공개 요청은 존재/미존재/미등록/제한 초과에 같은 접수 응답을 반환합니다. 메일 대기 제한 8초보다 긴 공통 접수 시간 하한을 사용합니다. 과부하·DB 지연까지 일정한 시간을 보장하는 부하 검증 결과는 아닙니다. 운영에서는 지연과 발송 도달률을 따로 확인해야 합니다. 프록시 때문에 클라이언트 IP가 한 주소로 보이면 제한이 더 보수적으로 적용될 수 있습니다.

## 운영 적용과 후속 확인

1. 승인한 운영 스키마에서 변경 전 22개 표·52,144행의 비공개 스냅샷 백업을 검증했습니다. 검증 범위는 동일 시점의 스키마·표별 행 수, 백업 형식과 DPAPI 암호화 후 복호화 바이트 일치입니다. 별도 DB에 실제 복원한 시험은 수행하지 않았습니다. 기존 Preview·Manus 원본은 변경하지 않았습니다.
   [메타데이터 전용 사전 점검 도구](ACCOUNT_RECOVERY_PREFLIGHT.md)로 대상 상태를 확인한 뒤 승인된 [수동 추가 마이그레이션](../drizzle/account_recovery.sql)의 DDL 4문만 순서대로 적용하고 `ready`를 확인했습니다. `db:push`나 전체 파일 자동 재실행으로 대체하지 않습니다.
2. 이번 운영 배포는 `auth_version`과 복구 테이블 3개를 준비하고 확인한 뒤 진행했습니다. 이후 이 코드를 다른 DB에 배포할 때도 먼저 스키마를 준비해야 합니다. 기존 로그인도 users 컬럼을 읽으므로 활성화 플래그 0만으로 누락 컬럼 문제를 피할 수 없습니다.
3. Brevo의 전화 인증·발신 주소 Verified 상태를 확인했고, 분리 QA 5건과 운영 5건의 메일 수신을 별도로 확인했습니다. Preview의 인증·재설정 링크에서는 origin·경로·token fragment 보존과 앱에서의 fragment 제거도 확인했습니다. 실제 QA 메일 헤더에는 Brevo의 `brevosend.com` 발신 주소 대체가 보였으며, 소유한 SemiGuard 발신 도메인을 검증한 것은 아닙니다. 공식 안내는 장기적으로 소유 도메인 인증을 권장합니다. 운영 서버 Secret 등록·정식 origin 설정·메일 활성화는 승인 후 완료했으며, 도메인 구매·DNS 변경·유료 약정은 하지 않았습니다. 이번 INBOX 도달로 다른 수신자·스팸 분류·운영 도달률을 보장하지 않으며, 추적·링크 가공이 꺼져 있다고 가정하지 않습니다.
4. 다음 값은 서버 전용으로 환경별 설정합니다. `VITE_` 접두어를 붙이지 않고 개발용 값과 운영 값을 분리합니다.

| 변수 | 값 종류 |
| --- | --- |
| `SEMIGUARD_ACCOUNT_RECOVERY_ENABLED` | 기본 미설정/0. 현재 운영은 승인 후 1로 활성화 |
| `RECOVERY_MAIL_API_KEY` | 승인된 Brevo API 키를 서버 Secret으로 저장. 실제 키 권한은 계정 콘솔에서 확인하고 가능한 최소 범위 사용 |
| `RECOVERY_MAIL_FROM` | Brevo에서 검증한 발신 이메일 주소만 입력. 어댑터는 발신자 이름 `SemiGuard AI`를 별도 전달 |
| `RECOVERY_PUBLIC_ORIGIN` | 기존 공개 사이트의 HTTPS origin. 경로·인증정보·query·fragment 없음 |

운영용 메일 키는 1개월 키로, 확인한 만료일은 **2026-12-02**입니다. 만료 전에 운영용 키를 갱신하고 서버 Secret을 교체해야 합니다. 이 작업은 기존 DB 연결이나 세션·공유 서명 키를 교체하는 작업과 구분합니다. 운영에서는 분리 QA용 `SEMIGUARD_RECOVERY_QA`와 `VITE_RECOVERY_QA`를 0/미설정으로 유지해야 합니다.

5. 분리 Preview의 합성 계정에서는 사용자가 직접 등록·인증·비밀번호 재설정·새 비밀번호 로그인을 마쳤습니다. 이메일 기반 재설정은 실제 메일과 입력 화면 열기까지만 확인했으며 두 번째 재설정은 하지 않았습니다. 인증 과정에서 한 번 표시된 일반 invalid-link 응답의 정확한 순서·원인은 미확정이므로 통제된 재사용 거절 검증으로 기록하지 않습니다. 같은 브라우저는 쿠키를 공유하므로 현재 세션 해제만으로 별도 브라우저의 이전 JWT 거절을 증명하지 않습니다. 앞선 실제 DB·세션 버전 검증은 이 브라우저 결과와 구분합니다.
   별도 승인한 운영 합성 계정 1개·수신함 1개·최대 5회 발송 범위에서 인증·아이디 안내·아이디 기반 재설정·변경 알림·이메일 기반 재설정 메일 5건의 INBOX 도달을 확인했습니다. 사용자가 최신 원본 링크를 다시 열어 새 시험 비밀번호 변경을 완료했고, 기존 보호된 계정 탭을 새로고침했을 때 로그인 화면으로 이동했습니다. 이후 사용자가 새 비밀번호로 직접 로그인했고 실제 `/training`과 `/account`에서 동일한 `Synthetic production recovery QA` 계정·인증 이메일을 확인했습니다. 처음 사용자가 설명한 만료 안내의 정확한 원인은 미확정이며 재발송은 하지 않았습니다. 다섯 번째 이메일 방식은 실제 수신과 메일 본문의 정식 origin·재설정 경로·토큰 형식까지만 확인했으며, 입력 화면을 열거나 두 번째 변경을 제출하지 않았습니다. 사용자 직접 회원탈퇴 후 정확한 시험 계정·복구 이메일·토큰 삭제와 임시 연결정보 삭제·도우미 종료를 확인했습니다. 승인한 5회 시험 발송을 모두 사용했으므로 추가 시험 메일은 새 승인 없이 보내지 않습니다. 실패·시간 초과도 이 한도에 포함하며, 이 운영 확인을 이전 분리 QA의 5건 수신·6회 제한과 합산하거나 혼동하지 않습니다. 기존 회원 기록은 테스트로 바꾸지 않습니다.
6. 승인된 PR #103을 main `5be15513`으로 병합·배포하고 운영 메일을 활성화했습니다. 사용자 직접 탈퇴 후 정확한 시험 계정·복구 이메일·토큰이 없음을 읽기 전용으로 확인했습니다. 공유 제한 카운터와 인증 차단값은 보존했고, 임시 연결정보를 지운 상태와 점검 도우미 종료를 확인했습니다. 비활성 상태는 ‘준비 중’이며 발송 성공을 가장하지 않습니다.

롤백 시 새 테이블·컬럼과 세션 버전을 삭제하거나 낮추지 않습니다. 재설정 후 버전 검증이 없는 서버 코드로 되돌리면 이전 세션이 다시 유효해질 수 있으므로 버전 검사 유지 패치가 필요합니다. 발송만 중단하려면 플래그를 0으로 두고 세션 검사는 유지합니다.

## 검증 근거

최종 실행 명령·결과와 남은 실제 환경 검증은 [HANDOFF](HANDOFF.md)를 따릅니다. 가상 저장소/메일 테스트나 브라우저 응답 fixture는 운영 TiDB 트랜잭션·실제 수신 성공의 증거가 아닙니다.
