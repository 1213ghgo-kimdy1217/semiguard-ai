# 계정 찾기·비밀번호 재설정

상태: 별도 브랜치에서 승인된 분리 TiDB·Vercel Preview·실제 메일 검증을 완료했습니다. 운영 스키마 변경·메일 Secret 등록·main 병합·공개 배포는 아직 승인되거나 수행되지 않았습니다.

2026-11-02 진행: 사용자가 승인한 Gmail로 Brevo 무료 계정과 전화 인증을 완료했고, 실제 화면에서 해당 발신 주소의 Verified 상태를 확인했습니다. 소유 도메인 인증은 하지 않았습니다. 사용자가 생성한 1개월·Transactional email 전용 키는 이번 브랜치의 Vercel Preview Secret에만 저장했습니다. Brevo REST 어댑터를 통한 인증·아이디 안내·아이디 기반 재설정·변경 알림·이메일 기반 재설정 메일 5건을 실제 INBOX에서 확인했습니다. 환경값과 명시적 활성화 플래그가 없으면 발송하지 않습니다. 이 결과는 분리 QA의 증거이며 운영 연결·발송 성공을 뜻하지 않습니다.

분리 QA DB에서는 합성 계정 4개로 실제 TiDB 트랜잭션·동시 재설정·실패 시 원복·제한·세션 버전 등 18/18 항목을 확인하고 해당 계정을 정리했습니다. 누적 다섯 번째 합성 계정으로 실제 Preview 로그인과 메일 왕복을 확인한 뒤, 정확한 ID/openId의 계정·복구 이메일·토큰만 정리했습니다. 모든 공유 제한 카운터와 최대 6회 발송 시도 예산은 보존했고, 임시 연결정보를 지운 상태와 로컬 도우미 종료도 확인했습니다. 실제 회원 자료를 복사하거나 변경하지 않았습니다.

## 이용 흐름

- 로그인 화면의 회원가입 옆에서 **아이디 찾기 / 비밀번호 재설정**을 선택합니다.
- 아이디 찾기는 사전에 인증한 복구 이메일로 아이디를 보냅니다. 결과 화면에 회원정보나 계정 존재 여부를 표시하지 않습니다.
- 비밀번호 재설정은 **로그인 아이디 / 등록된 복구 이메일** 중 하나를 입력하고, 해당 계정의 인증된 복구 이메일로 받은 링크를 이용합니다.
- 기존 계정은 로그인할 수 있을 때 **계정 관리 → 복구 이메일 → 현재 비밀번호 재확인 → 이메일 링크 인증**을 먼저 해야 합니다. 기존 일반 회원가입은 이메일을 받지 않았으므로 이미 이메일 복구가 가능하다고 소급하여 주장하지 않습니다.
- 이메일을 인증하지 못한 계정은 이 기능으로 복구할 수 없습니다. 사전에 연결해 둔 소셜 로그인은 기존 방식대로 이용합니다. 이름·생년월일·공개 아이디만으로 비밀번호를 바꾸지 않습니다.
- 링크는 15분/1회용입니다. 새 비밀번호는 10~128자로 두 번 입력하고, 완료 후 새 비밀번호로 다시 로그인합니다. 기존 가입/로그인 요청 필드와 기존 비밀번호는 그대로 호환됩니다.

## 보존하는 계약

기존 회원 ID/openId, 비밀번호 해시, 소셜 제공자 ID 연결, 학습 기록·답안·점수·이어하기·공유·AI 동의 계약을 바꾸지 않습니다. 이메일이 같다는 이유로 소셜 계정을 연결하거나 기존 `users.email` 및 소셜 이메일을 인증 완료로 취급하지 않습니다.

세션 버전 `users.auth_version`의 초기값은 0입니다. 버전 없는 기존 세션은 버전 0 계정에 한해 유효합니다. 재설정은 토큰 확인/소비·해시 교체·버전 증가·기존 복구 토큰 제거를 한 트랜잭션에서 처리하고 이전 쿠키와 Bearer 세션을 차단합니다. 탈퇴 시 복구 이메일과 미사용 토큰도 같은 트랜잭션에서 제거합니다.

## 저장·전송 범위

| 항목 | 처리 |
| --- | --- |
| 복구 이메일 | 별도 테이블에 소유 확인 주소와 시각 저장. 계정당 하나, 확인 주소 키는 고유 제약. 기존 프로필 주소를 자동 수입하지 않음 |
| 일회용 토큰 | 32바이트 난수 원문은 메일로 전달, DB에는 SHA-256 해시·목적·계정·주소·언어·세션 버전·만료만 저장 |
| 남용 방지 | DB 기반 전역/클라이언트/입력값 제한과 최종 수신함 제한. 서버 키로 해시한 카운터만 저장하고 만료분을 제한된 수로 정리 |
| 브라우저 | URL fragment를 즉시 제거. local/sessionStorage에 토큰을 저장하지 않고 요청 뒤 비밀번호와 변경 요청 캐시 정리 |
| 메일 제공자 | Brevo 트랜잭션 REST 어댑터. 명시적 활성화 시 고정 HTTPS API로 발신·수신 주소와 안내 문구/아이디 또는 일회용 링크를 전송. 텍스트 본문만 사용하고 비밀번호·회원 답안은 보내지 않음 |
| 분석·로그 | 복구 경로는 기존 GA 페이지 허용 목록에 포함하지 않음. 복구 변경 요청의 전송 오류 객체·수신자·토큰·제공자 응답 본문을 출력하지 않음 |

공개 요청은 존재/미존재/미등록/제한 초과에 같은 접수 응답을 반환합니다. 메일 대기 제한 8초보다 긴 공통 접수 시간 하한을 사용합니다. 과부하·DB 지연까지 일정한 시간을 보장하는 부하 검증 결과는 아닙니다. 운영에서는 지연과 발송 도달률을 따로 확인해야 합니다. 프록시 때문에 클라이언트 IP가 한 주소로 보이면 제한이 더 보수적으로 적용될 수 있습니다.

## 운영 적용 전 필요한 승인·준비

1. 운영과 preview 각각의 스키마 변경 범위, 백업/복원 절차를 검토합니다. [수동 추가 마이그레이션](../drizzle/account_recovery.sql)은 자동 실행하지 않습니다. `db:push`로 대체하지 않습니다.
   [메타데이터 전용 사전 점검 도구](ACCOUNT_RECOVERY_PREFLIGHT.md)는 미적용/완료/부분 적용을 구분합니다. 승인된 분리 QA DB의 스키마 준비와 실제 DB 검증은 완료했으나, 운영과 기존 Preview DB에는 이 기능의 스키마 변경을 하지 않았습니다.
2. **이 코드를 배포하기 전에** 대상 DB에 `auth_version`과 복구 테이블 3개를 준비해야 합니다. 기존 로그인도 users 컬럼을 읽으므로 활성화 플래그 0만으로 누락 컬럼 문제를 피할 수 없습니다.
3. Brevo의 전화 인증·발신 주소 Verified 상태와 이번 QA 브랜치 전용 Secret 저장을 확인했고, 승인한 수신함에 실제 메일 5건이 도달했습니다. 받은 인증·재설정 링크의 Preview origin·경로·token fragment 보존과 앱에서의 fragment 제거도 확인했습니다. 실제 메일 헤더에는 Brevo의 `brevosend.com` 발신 주소 대체가 보였으며, 소유한 SemiGuard 발신 도메인을 검증한 것은 아닙니다. 공식 안내는 장기적으로 소유 도메인 인증을 권장합니다. 도메인 구매·DNS 변경·유료 약정·운영 Secret 등록·운영 발송은 수행하지 않았습니다. 이번 INBOX 도달로 다른 수신자·스팸 분류·운영 도달률을 보장하지 않으며, 추적·링크 가공이 꺼져 있다고 가정하지 않습니다.
4. 다음 값은 서버 전용으로 환경별 설정합니다. `VITE_` 접두어를 붙이지 않고 개발용 값과 운영 값을 분리합니다.

| 변수 | 값 종류 |
| --- | --- |
| `SEMIGUARD_ACCOUNT_RECOVERY_ENABLED` | 기본 미설정/0. 승인 후 1 |
| `RECOVERY_MAIL_API_KEY` | 승인된 Brevo API 키를 서버 Secret으로 저장. 실제 키 권한은 계정 콘솔에서 확인하고 가능한 최소 범위 사용 |
| `RECOVERY_MAIL_FROM` | Brevo에서 검증한 발신 이메일 주소만 입력. 어댑터는 발신자 이름 `SemiGuard AI`를 별도 전달 |
| `RECOVERY_PUBLIC_ORIGIN` | 기존 공개 사이트의 HTTPS origin. 경로·인증정보·query·fragment 없음 |

5. 분리 Preview의 합성 계정에서 사용자가 직접 기존 비밀번호로 로그인하고 복구 이메일 등록을 요청했습니다. 인증 상태 재조회로 저장된 인증 이메일을 확인했고, 아이디 안내 메일의 정확한 합성 아이디와 아이디 기반 재설정 메일·입력 화면을 확인했습니다. 사용자가 직접 새 비밀번호를 입력해 재설정한 뒤 변경 알림 수신과 현재 브라우저의 로그인 화면 이동, 새 비밀번호 로그인 후 동일 합성 계정·인증 이메일 표시를 확인했습니다. 이메일 기반 재설정은 실제 메일과 입력 화면 열기까지만 확인했으며 두 번째 재설정은 하지 않았습니다. 인증 과정에서 한 번 표시된 일반 invalid-link 응답의 정확한 순서·원인은 미확정이므로 통제된 재사용 거절 검증으로 기록하지 않습니다. 같은 브라우저는 쿠키를 공유하므로 현재 세션 해제만으로 별도 브라우저의 이전 JWT 거절을 증명하지 않습니다. 앞선 실제 DB·세션 버전 검증은 이 브라우저 결과와 구분합니다. 운영 확인에 사용할 합성 계정·수신 주소와 범위는 별도 승인하며 기존 회원 기록을 테스트로 바꾸지 않습니다.
6. 위 결과를 확인한 뒤 main 병합과 공개 배포 승인을 받습니다. 비활성 상태는 ‘준비 중’이며 발송 성공을 가장하지 않습니다.

롤백 시 새 테이블·컬럼과 세션 버전을 삭제하거나 낮추지 않습니다. 재설정 후 버전 검증이 없는 서버 코드로 되돌리면 이전 세션이 다시 유효해질 수 있으므로 버전 검사 유지 패치가 필요합니다. 발송만 중단하려면 플래그를 0으로 두고 세션 검사는 유지합니다.

## 검증 근거

최종 실행 명령·결과와 남은 실제 환경 검증은 [HANDOFF](HANDOFF.md)를 따릅니다. 가상 저장소/메일 테스트나 브라우저 응답 fixture는 운영 TiDB 트랜잭션·실제 수신 성공의 증거가 아닙니다.
