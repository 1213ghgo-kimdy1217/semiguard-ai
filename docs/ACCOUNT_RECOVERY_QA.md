# 분리된 TiDB 계정 복구 QA

승인된 테스트 대상은 기존 사용자 소유 무료 클러스터의 **`semiguard_recovery_qa_20261102`**뿐입니다. 이 도구는 운영 DB·Manus 원본·기존 Preview를 대상으로 실행하지 않습니다. 코드 추가나 오프라인 테스트는 실제 DB 검증 완료를 뜻하지 않습니다.

## 준비와 실행

```powershell
node --import tsx scripts/qa-account-recovery-tidb.ts --help
node --import tsx scripts/qa-account-recovery-tidb.ts --prepare-sql
```

두 명령은 DB에 연결하거나 환경 값을 읽지 않습니다. 두 번째는 위 이름으로 된 QA DB와 정확히 다섯 테이블(`users`, `account_revocations`, 복구 테이블 3개)의 검토용 DDL만 출력하며 실행하지 않습니다. 회원 테이블 전체 컬럼은 앱과 호환되지만 실제 사용자 행은 복사하지 않습니다. 기존 수동 마이그레이션이 포함되어 있어 중복 실행은 하지 않습니다. `DROP`, `db:push`, 운영 스키마 변경은 포함하지 않습니다.

운영자가 비공개 연결 화면에서 승인된 QA 대상임을 확인하고 프로세스 전용 `DATABASE_URL`과 별도로 확인한 `RECOVERY_QA_EXPECTED_HOST`·`RECOVERY_QA_EXPECTED_USER`를 모두 제공한 뒤에만 다음 명령을 실행합니다. 공유 게이트웨이 호스트만으로는 승인된 클러스터/테넌트를 구분할 수 없으므로, 사용자 이름도 URL에서 자동 추출하지 않고 따로 고정해야 합니다. 비밀번호·접속 URL·실제 사용자 이름을 명령행 인수·채팅·공개 로그·Git 파일에 넣지 않습니다. `.env`를 불러오지 않습니다.

```powershell
node --import tsx scripts/qa-account-recovery-tidb.ts --run
```

URL에서 DB명·별도 지정한 소유 클러스터 호스트·사용자 이름·포트 4000이 정확히 일치해야 연결 시도를 시작합니다. 별도 사용자 이름이 누락되거나 다른 경우, 실행 함수와 준비 함수 모두 연결 전에 중단합니다. 실제 연결 후에도 `DATABASE()` 일치 여부를 다시 검사합니다. 인증서·호스트명 검증을 모두 켜고, 다섯 테이블만 존재하며 모두 비어 있어야 가상 행을 추가합니다. QA 창을 독점하여 다른 Preview나 테스트가 동시에 이 DB에 쓰지 않도록 합니다. 기본 인수 없는 실행은 도움말만 보여 줍니다.

인증정보를 파일이나 환경에 넣지 않는 로컬 입력 화면은 같은 모듈의 `prepareRecoveryQaDatabase(privateUrl, { expectedHost, expectedUser })`와 `runRecoveryQa(privateUrl, { expectedHost, expectedUser })`를 각각 호출할 수 있습니다. 모듈을 import하는 것만으로는 환경을 읽거나 연결하지 않습니다. 별도로 확인한 호스트와 필수 사용자 이름을 URL 값과 대조합니다. 두 함수는 비밀값 없는 boolean 결과만 반환하고 직접 출력하지 않습니다.

준비 함수는 명시적으로 호출된 경우에만 DB 없는 클러스터 연결에서 **정확한 QA 이름**을 생성하고 QA DB에 다시 연결합니다. 완전히 빈 스키마에서만 검토된 여섯 DDL 문으로 다섯 테이블을 준비합니다. 이미 준비된 스키마는 변경하지 않고 검사하며, 부분 적용·예기치 않은 테이블이 있으면 자동 수리 없이 중단합니다. 준비와 실제 QA 실행은 분리된 작업입니다. 운영 스키마에는 연결하지 않습니다.

## 비공개 입력창과 Preview 이어하기

`node --import tsx scripts/recovery-qa-console.ts`는 `127.0.0.1:4319`에서 비공개 입력창을 엽니다. 독립 확인한 호스트·사용자 이름을 먼저 고정하고 사용자가 기존 DB 비밀번호를 직접 입력하면 준비와 네 계정 시험을 한 번만 실행합니다. URL·비밀번호는 서버 메모리에만 두며, 통과 후 사용자의 복사 버튼으로만 Vercel의 이번 브랜치 Secret에 전달합니다. 성공 여부가 불확실하면 자동 재시도하지 않습니다.

네 계정 시험과 정리가 완료되고 기존 입력창의 임시 정보를 지운 뒤에는 `node --import tsx scripts/recovery-qa-console.ts --preview-only`로 `127.0.0.1:4320`에서 이어갑니다. 이 모드는 정확한 다섯 테이블과 빈 사용자 범위만 확인하며 기존 네 계정 시험을 재실행하지 않습니다. 사용자가 별도 시험 비밀번호를 직접 정해 가상 계정 한 개를 만듭니다. 누적 다섯 번째 계정이며, 여러 입력창을 동시에 실행하지 않습니다. 고정 로그인 아이디는 `SEMIGUARD-RECOVERY-QA-20261102`입니다. 새 Preview 서명 키는 메모리에서 생성하고 별도 복사 버튼으로만 전달하며, 운영 키는 읽거나 재사용하지 않습니다.

브라우저와 메일 검증 후에는 동일 입력창의 정리 버튼으로 캡처한 ID·openId가 일치하는 이 계정의 사용자·복구 이메일·토큰만 정리합니다. 탈퇴 검증은 하지 않으며 알 수 없는 탈퇴 마커가 있으면 정리를 중단합니다. 계정 정리에서 `account_recovery_limits`는 건드리지 않습니다. 생성·정리 결과가 불확실하면 입력창을 닫거나 다시 실행하지 말고 검토합니다. 사용자 입력을 기다릴 때 프로세스와 탭을 유지해야 합니다.

### 이미 만든 Preview 계정의 연결창만 중단된 경우

`--preview-only`나 네 계정 시험을 다시 시작하지 않습니다. `node --import tsx scripts/recovery-qa-console.ts --recover-preview`는 현재 소유 서버·사용자와 기존 비밀번호를 직접 확인한 뒤, 정확한 QA 스키마의 유일한 알려진 합성 계정만 읽기 전용으로 확인합니다. 새로운 계정·서명 키는 만들지 않고 기존 Preview 키를 유지합니다. 합성 소유자만 기록한 감사 파일은 Git 밖의 `work/verification-artifacts`에 두며, 비밀번호·주소·토큰·해시는 기록하지 않습니다. 다른 소유자·이미 정리된 감사 기록·여러 계정·부분 스키마에서는 복구하지 않습니다.

정리 성공 뒤에는 `browserPhase: cleaned`, `cleanupRequired: false`를 확인하고 **임시 연결정보 지우기**를 실행합니다. 이어 `configured: false`, `phase: forgotten`을 확인한 뒤 도우미를 종료합니다. 탭을 닫는 것만으로 서버 메모리가 지워졌다고 취급하지 않습니다. 정리 상태가 불확실하면 재실행·재생성·강제 종료 대신 상태를 검토합니다.

Preview는 정확한 복구 브랜치·분리 QA DB·TLS 검증 설정에서만 API를 허용합니다. 로그인·복구와 필요한 상태 조회 외 회원가입·OAuth·AI·학습 저장·외부 파일 저장은 차단합니다. 실제 메일 수신자는 승인한 Gmail 하나로 제한하며, 모든 인스턴스가 공유하는 DB 예산을 발송 **전** 예약합니다. 실패와 시간 초과도 전체 여섯 번에 포함됩니다. 새 키·재배포·가상 계정 정리로 예산을 초기화하지 않습니다. `RECOVERY_QA_MAIL_BUDGET_KEY` 행을 삭제하거나 수정하지 않습니다.

## 검증 범위

- 실제 mysql2 연결 풀·Drizzle 트랜잭션과 앱의 복구 서비스를 사용합니다. 자동 생성 ID와 실행별 UUID를 가진 합성 비밀번호 계정 **4개**를 만들며 최대 6개 승인 범위 안에 머뭅니다.
- 동일 토큰의 동시 재설정에서 한 번만 성공하고 해시·세션 버전·토큰 제거가 함께 반영되는지 확인합니다. 재사용 거절도 확인합니다.
- 테스트 전용 주입 어댑터가 비밀번호 변경과 토큰 삭제 뒤 의도적으로 실패시켜 실제 DB 트랜잭션이 해시·버전·토큰을 모두 원복하는지 확인합니다. 운영 코드나 서버 설정에 실패 모드를 추가하지 않습니다.
- 서로 다른 계정의 동일 이메일 인증을 저장 직전 동기화하여 실제 고유 제약 충돌에서 한 소유자만 남는지 확인합니다.
- 새 서비스 인스턴스·아이디/이메일 방식·아이디 안내/비밀번호 목적 사이에서 최종 수신함 제한을 공유하는지 확인합니다.
- 저장된 실제 토큰에 대해 **주입한 앱 시계만** 15분 이후로 이동시켜 만료 거절을 확인합니다. 서버 시간·DB 시스템 변수는 바꾸지 않으며 실제 15분 경과 대기 검증으로 주장하지 않습니다.
- 실제 서명/검증한 합성 JWT와 세션 버전 비교 함수를 검증합니다. 실제 브라우저 쿠키·OAuth·로그인 완료 검증은 별도로 필요합니다.

메일은 `example.invalid` 주소를 쓰는 고정된 메모리 수신함으로만 전달합니다. 외부 이메일·Brevo 요청은 **0회**이며, 승인된 실제 메일 6회 한도를 소비하지 않습니다. 공개 API 최소 응답 대기시간·SMTP/메일 수신·브라우저 왕복을 검증한 것으로 취급하지 않습니다. 앱 키를 재사용하지 않고 메모리의 일회성 QA 키를 이메일/제한/탈퇴 해시에 명시적으로 주입합니다.

## 정리와 결과

테스트 전용 어댑터는 전체 만료 정리를 호출하지 않습니다. 다른 실행의 만료 행까지 삭제하지 않기 위한 것으로, 전체 만료 정리 SQL의 실제 실행 검증은 이번 범위에 포함하지 않습니다.

`finally`에서 실행 UUID의 정확한 계정 식별자와 생성 ID를 다시 확인하고 해당 계정의 토큰·이메일·탈퇴 마커, 이번 실행에서 추적한 제한 키만 삭제합니다. 다른 행·스키마를 삭제하거나 자동 증가 번호를 초기화하지 않습니다. QA 스키마와 다섯 빈 테이블은 유지합니다. 정리 실패 시 중단하고 검토하며, 광범위한 DELETE/TRUNCATE/DROP으로 보완하지 않습니다.

출력은 고정된 검증 항목의 통과/실패 boolean뿐입니다. 비밀번호·해시·토큰·이메일·URL·DB 원문 오류·UUID는 출력하지 않습니다. 모든 검증과 실행 소유 행 정리가 통과해야 종료 코드 0이며, 실패는 1입니다. 프로세스 강제 종료·네트워크 끊김에서는 정리가 완료되지 않을 수 있으므로 자동 재시도하지 말고 먼저 QA DB를 비공개로 확인합니다.

운영 적용은 이 결과와 별개입니다. [스키마 사전 점검](ACCOUNT_RECOVERY_PREFLIGHT.md), 실제 테스트 메일 왕복, Preview 확인과 운영 변경 승인을 각각 완료해야 합니다.

2026-11-02 실제 실행은 완료되었습니다. 앞의 네 합성 계정 시험과 별도로 다섯 번째 합성 계정에서 Preview 로그인·복구 이메일 인증 상태·아이디 안내·아이디 기반 재설정·변경 알림·새 비밀번호 로그인·이메일 기반 링크 화면을 확인했습니다. 실제 받은 메일은 5건이며, 이메일 기반 링크에서는 두 번째 재설정을 제출하지 않았습니다. 합성 계정과 그 복구 자료를 정리하고 임시 연결정보 삭제·도우미 종료를 확인했습니다. QA 표와 공유 제한 행은 유지하므로 현재 모든 표가 비었다고 가정하거나 발송 예산을 초기화하지 않습니다. 정확한 관측과 미검증 항목은 [HANDOFF](HANDOFF.md)를 따릅니다. 이 완료 기록은 시험 재실행 승인이 아닙니다.
